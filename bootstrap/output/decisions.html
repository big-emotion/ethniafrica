Decisions (DEC-NNN)

This page records the canonical product and engineering decisions of EthniAfrica.

DEC-001 — Use Confluence as the engineering intent source of truth

Status: Approved

Context: Requirements, decisions, architecture contracts, Jira tickets, code, and tests need stable identifiers and one explicit direction of intent.

Decision: Canonical engineering intent lives in the ETHNIAFRIC Confluence tree; Jira, code, and tests reference REQ-NNN, DEC-NNN, and ARCH-NNN identifiers.

Alternatives: Keep repository documents as the only source of truth, or duplicate mutable intent across Confluence and Git.

Tradeoffs: Confluence availability and disciplined identifier propagation become workflow dependencies, while repository snapshots remain auditable implementation evidence.

DEC-002 — Keep the existing brownfield foundation

Status: Approved

Context: EthniAfrica already has a production-shaped Next.js, Supabase, AFRIK, and test foundation with project-specific invariants.

Decision: Evolve the existing repository instead of adopting a starter template or rebuilding the application shell.

Alternatives: Generate a new starter application and migrate features into it.

Tradeoffs: The team preserves proven behavior and technical debt together, and must reconcile old documentation continuously.

DEC-003 — Model provenance per assertion

Status: Approved

Context: Fiche-level source lists cannot represent which source supports which factual assertion or how confidence was computed.

Decision: Use normalized sources, assertion links, immutable revisions, confidence scores, flags, and verification logs as the provenance fabric.

Alternatives: Keep one undifferentiated sources array per fiche or store provenance only in free-form JSON.

Tradeoffs: The normalized model adds joins and migration work but makes confidence, auditing, and public traceability computable.

DEC-004 — Use immutable @v{n} citation URLs

Status: Approved

Context: Printed and academic citations must continue to resolve to the exact content that was cited.

Decision: Pinned fiche revisions use /{lang}/{entity}/{slug}@v{n}; the route serves the stored revision snapshot rather than current data.

Alternatives: Use query parameters, opaque revision UUIDs, timestamps, or only a mutable canonical URL.

Tradeoffs: The readable scheme is durable and citable but becomes a permanent public compatibility contract.

DEC-005 — Use Supabase Auth with a queryable role table

Status: Approved

Context: Contributor, moderator, advisor, and administrator workflows need auditable identity and role checks beyond the retired shared admin cookie.

Decision: Use Supabase Auth for identity and user_roles keyed by auth.uid() for authorization.

Alternatives: Store roles only in user metadata or retain a shared username/password cookie.

Tradeoffs: Role joins and RLS policies add implementation work but centralize authorization in an auditable model.

DEC-006 — Keep a stable API envelope with embedded attribution

Status: Approved

Context: External consumers need predictable response parsing, lawful reuse metadata, and advance notice of breaking changes.

Decision: Keep stable major-version envelopes, embed license and canonical revision metadata, publish OpenAPI 3.1, and require a minimum six-month deprecation window.

Alternatives: Return resource-specific ad hoc payloads or rely on documentation outside the response.

Tradeoffs: Compatibility limits rapid contract changes but makes integrations and citations safer.

DEC-007 — Use Upstash Redis for distributed rate limiting

Status: Approved

Context: API-key and anonymous-write limits must survive client bypasses and work across stateless Vercel instances.

Decision: Enforce rate-limit buckets server-side through Upstash Redis, with documented fallback behavior when configuration is absent.

Alternatives: Use process-local memory, Vercel middleware-only limits, or a custom Supabase Edge Function.

Tradeoffs: A managed dependency adds latency and operating configuration but provides shared state across instances.

DEC-008 — Keep CC-BY-SA-4.0 content licensing and resolve the code license

Status: Pending

Context: Data reuse needs explicit attribution and share-alike terms, while the repository does not yet carry the required top-level permissive code license.

Decision: Keep CC-BY-SA-4.0 for content and select either MIT or Apache-2.0 for code before claiming full NFR41 compliance.

Alternatives: Use a non-share-alike data license, leave licensing implicit, or choose a non-permissive code license.

Tradeoffs: Share-alike improves commons reciprocity but constrains downstream relicensing; the unresolved code choice remains visible.

Requirements satisfied:

DEC-009 — Use EU-region managed infrastructure and privacy-conscious observability

Status: Approved

Context: The service processes contributor identity and usage telemetry while targeting users in Africa and the diaspora under GDPR obligations.

Decision: Host application and database workloads in EU regions, capture runtime errors in Sentry with PII scrubbing, and use consent-aware Plausible analytics.

Alternatives: Use region-agnostic defaults, invasive analytics, or operate custom observability infrastructure.

Tradeoffs: Regional and privacy constraints reduce vendor flexibility but simplify the stated compliance posture.

DEC-010 — Tighten demographic validation in two stages

Status: Approved

Context: The doctrinal demographic total is 100%, but legacy fiches do not all satisfy a strict one-percent tolerance yet.

Decision: Keep a temporary hard gate of 95–105%, emit a strict warning outside 99–101%, require new or changed fiches to target 99–101%, then tighten the hard gate after migration.

Alternatives: Block all legacy data immediately at 99–101% or keep the wider tolerance indefinitely.

Tradeoffs: The transition avoids freezing all data work while temporarily accepting a known gap against the final doctrine.
